# Agent 开发期使用协议（数据飞轮）

> 本文档回答：**使用仍处于开发期的 Idea Forge 时，agent 如何正确地"用"，以及如何把发现的问题反馈回来，让平台在使用中进化。**
>
> 适用对象：所有连接 Idea Forge MCP 的 agent。**开始干活前必读。**

---

## 一、平台状态声明

Idea Forge 是 **v0.1 开发中平台**（见 README「技术栈与状态」「路线图」）。由此导出三条行为准则：

1. **接口不承诺稳定**：工具签名、返回结构、实体字段随时可能调整，一切以 MCP 实际返回为准，不要假设"上次能用的这次还能用"。
2. **设计缺口是常态**：遇到工具难用、缺能力、语义矛盾，不是你的错——但报告它是你的义务（见 §四）。
3. **沉淀不因升级丢失**：磁盘 JSON 是唯一真相（可重建索引、可迁移），你落下的记录是安全的；只有"留在对话里没落库的东西"才会丢。

---

## 二、平台的角色——当前假设（会随实践修订）

> 本节是**开发期默认假设**，不是不可违背的规范。遇到反例（例如某些场景"先查平台再动手"确实更优、或某类记录不该急着落库），按实际合理性处理，并把反例写进 FEEDBACK.md——本协议随实践修订。目前假设：

1. **平台偏向"过程记录"定位**：实验做完、结果亲眼确认后，再把过程与结论落库，而不是用平台当记忆缓存反复查询。但这只是默认倾向，不是禁令——查询成本低且有助于对齐上下文时，查也无妨。
2. **落库的主要价值是跨会话、给人看、以及后续的知识沉淀**。同会话内你自带上下文，原则上不必反复查询自己刚做过的事；是否"反复"没有硬标准，以不打断节奏、不浪费上下文为准，自行判断。
3. **记录尽量能脱离你而存在**：description 写一句话意图、结论挂证据、判断给 rationale。但没有统一"合格线"——拿不准时凭常识先落下，再修订；粗糙的记录也优于只留在对话里。

## 三、使用守则（摘要）

研究操作流程（方案拆解、建 Idea/实验组/实验、结论沉淀）按 `docs/agent-workflow.md`（平台内已沉淀为 `skl-001 技术方案拆解`）。

- **权限边界**：只创建 / 受限变更；不硬删除、不覆盖已有结果；改状态走状态机。
- **证据门是硬约束**：`supported` 必须挂 evidence，无证据只能 `speculation`。
- **命名与备注**：实体 name 由你起，但要让人能看懂；ID 一律平台生成。

## 四、数据飞轮：发现即反馈

使用中遇到以下任何一类情况，都算"发现"，必须反馈：

| 类别 | 触发信号 |
|---|---|
| 工具问题 | 缺参数、语义歧义、报错信息误导、完成一个查询要 N+1 次调用、返回结构缺关键字段 |
| 数据问题 | 字段语义错位、状态机缺迁移、id/命名风格不一致、数据损坏（乱码/丢失） |
| 结构缺口 | 某种"过程性知识"（踩坑、临时判断、跨实验结论）当前**没有实体或字段能表达**——记录为"沉淀需求" |
| 设计矛盾 | 文档与实现不符、两处文档互相矛盾、工具行为与描述不一致 |

### 反馈方式

- **落点**：追加到平台本体仓库 `docs/FEEDBACK.md`（这是给平台开发者人审的清单，不是平台内数据）。
- **先查重**：追加前通读 FEEDBACK.md 已有条目；同类问题不再重复开，可在原条目下补充现场信息。
- **格式**：固定五要素，一个发现一条：

```markdown
## YYYY-MM-DD · <一句话标题>
- 触发：<当时在做什么、调用了什么工具/看了什么数据>
- 问题：<具体现象，含报错原文/数据样例>
- 影响：<不修会怎样，谁会踩坑>
- 建议：<最小改动方案，可选>
- 状态：pending
```

- **状态机**：`pending`（待审）→ `accepted`（已采纳）→ `done`（已修复），由人在文档中维护。
- **前车之鉴**：新会话的 agent 应先扫一眼 FEEDBACK.md 中 `pending`/`accepted` 条目——已知问题不要第二次报告，直接绕开或按建议规避。

### 反馈之后

反馈不是丢进黑洞：人被采纳后置 `accepted`，修复后置 `done` 并注明修复方式。你在后续会话中能查到自己的反馈进了平台下一版本——这是闭环，也是"平台是 agent 用出来的"的机制保证。

## 五、知识沉淀（过渡方案，完整知识库落地前）

平台的**跨会话知识库**（过程性知识沉淀为带实体索引的 md，供新会话一次加载、免于逐个调工具查询）已在规划中。落地之前，按以下规则分层沉淀：

| 要沉淀的东西 | 放哪 |
|---|---|
| 单点结论（验证了什么） | `create_claim`（挂 evidence） |
| 单实验复盘（怎么跑的、看到什么） | `write_analysis` |
| 可复用套路（怎么调参、怎么判据） | `create_skill`（draft 起步，验证后转 stable） |
| 跨越多个实验/阶段的过程性判断、踩坑、权衡 | 方向仓库 `docs/<idea-slug>-notes.md`，文中用 `@exp-xxx` / `@claim-xxx` / `@grp-xxx` 标注实体引用 |
| 平台本身的改进需求 | `docs/FEEDBACK.md`（见 §四） |

> 过渡期判断标准：一段知识若**下次会话的你或同组的人**大概率需要，就不要只留在对话里；找不到合适实体的，写 notes md 并用实体 id 做索引——这些 md 就是未来知识库的种子。

---

## 六、一句话总纲

**平台记过程，你记判断；会话可以断，沉淀不能断；发现问题不沉默，写进 FEEDBACK.md。**
