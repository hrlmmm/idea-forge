# Agent 自主研究工作流（技术方案 → 可执行研究计划）

> 本文档回答：**用户给一份研究技术方案，agent 如何自主把它变成 Idea Forge 里可追踪、可执行、可沉淀的研究计划。**
>
> 这不是平台代码，而是 agent 的操作规范——它本身也以 Skill 形式沉淀在平台里（`skl-001 技术方案拆解`），供 agent 加载复用。

---

## 一、核心心智模型

平台有 6 类实体，一条完整的研究链路是这样串起来的：

```
Direction（方向 = 一个仓库）
  → Idea（一份方案的载体）
    → ExperimentGroup（方案的"阶段"，dependsOn 表达闸门依赖）
      → Version（阶段要跑的代码 commit）
        → Experiment（具体实验，attach Skill 支持复现）
        → Analysis（跑完的复盘）
    → Claim（结论，证据门约束）
  → Skill（可复用的技能，agent 自己沉淀）
```

**一句话**：方案 → Idea；阶段 → 实验组（带依赖）；实验 → 落在组里；结论 → Claim（挂证据）；套路 → Skill。

---

## 二、拆解五步（对应 skl-001）

### 第 1 步：建 Idea（方案整体）

拿到方案，先建一个 Idea 承载它：

- `name` = 方案标题简写
- `hypothesis` = 方案要验证的核心命题（一句话，这是整个研究的靶心）

```
create_idea(direction_id, name="两阶段影响力最大化", hypothesis="粗排召回+精排排序，可在去 N² 后保持质量")
```

### 第 2 步：建实验组（每个阶段一个组，声明依赖）

方案的每个「阶段」= 一个实验组。关键是把**闸门依赖**显式建模：

- `purpose` = 该阶段要回答的问题 + 判据（如「判据 recall>=0.8」）
- `depends_on` = 上游阶段组的 id

依赖规则：方案里「阶段 X 是阶段 Y 的前置 / 闸门」→ Y 的 depends_on 含 X。

> 例：两阶段框架里，阶段 1（召回率验证）是闸门，阶段 2/3 都依赖它，阶段 4 依赖 2+3。

### 第 3 步：建 Version + 实验（每个阶段的具体实验）

对方案里列出的每个具体实验：

- `create_version` 记录该阶段要跑的那份代码（commit）
- `create_experiment` 把方案里明确的参数填进 `params`，`description` 写「这次验证什么」，`group_id` 归到对应阶段

### 第 4 步：跑完沉淀结论（Claim，证据门）

实验出结果后，对方案的每个「判据」沉淀结论：

- **有证据 → `supported`**，`evidence` 挂支撑它的实验 id
- **没证据 → 只能 `speculation`**（猜测）

证据门是硬约束：`supported` 不挂 evidence 会被服务端拒绝（返回 400）。

### 第 5 步：沉淀 Skill（套路复用）

跑通后，把「怎么跑这类实验、怎么判」固化成 Skill，下次同类实验直接 `attach`。

## 三、真实闭环验证（2026-09-01 已跑通）

用《两阶段框架》方案实测：

| 实体 | 结果 |
|---|---|
| Direction | `多层影响力最大化` |
| Idea | `两阶段影响力最大化框架`（hypothesis = 去 N² 后保持质量） |
| 实验组 ×6 | 阶段0复现瓶颈 → 阶段1召回率(闸门) → 阶段2粗排 / 阶段3精排（都依赖阶段1）→ 阶段4端到端（依赖2+3）→ 阶段5线性注意力（依赖4） |
| 实验 ×2 | 度中心性粗排 / PageRank 粗排（挂阶段1） |
| 结论 ×2 | `召回率>=0.8，两阶段成立`（supported，挂 2 实验证据）+ `阶段5线性注意力`（speculation） |
| 技能 ×1 | `技术方案拆解`（全局，跨方向复用） |

证据门实测：无 evidence 的 `supported` 结论 → 服务端拒绝，返回 `400 supported 结论必须有 evidence`。
